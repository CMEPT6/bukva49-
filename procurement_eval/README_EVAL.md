# Каркас оценки: закупочные лоты

Сравнивает три конфигурации на одном наборе лотов: `direct` (модель выбирает сама), `simple` (модель извлекает JSON, выбирает обычная функция), `bukva` (то же плюс проверка схемы и цитат и `BukvaAgentPipeline.run_spec`).

```bash
python eval_harness.py --check-gold                          # эталон согласован с правилами?
python eval_harness.py --backend mock-oracle                 # проверка самого каркаса
python eval_harness.py --backend ollama --model qwen3.5:9b --repeats 3 --out result.json
python -m unittest test_harness
```

## Формат лота (`lots_seed.json`)

| Поле | Что это |
|---|---|
| `text` | условия лота, как в объявлении (неструктурированный текст) |
| `offers_text` | предложения поставщиков, как их присылают |
| `method`, `rules_version` | способ закупки и редакция правил на дату лота |
| `gold.constraints` | ограничения, которые действительно есть в тексте (`null` = не указано) |
| `gold.quotes` | дословная цитата из `text` для каждого непустого ограничения |
| `gold.candidates` | предложения в структурированном виде, цены приведены к условиям сравнения лота |
| `gold.winner_id` | победитель по условиям лота; `null`, если допустимого нет (верный ответ - отказ) |

## Метрики

- **confidently_wrong** - доля ответов, где назван не тот победитель или назван победитель на лоте без победителя.
- **false_rejection** - доля отказов на лотах, где победитель существует.
- **correct_refusal** - доля верных отказов на лотах без победителя.
- **reproducibility** - доля лотов с одинаковым ответом при всех повторах.
- **extraction** - совпадение извлечённых ограничений и кандидатов с эталоном.

Интервалы считаются бутстрэпом по ответам. При числе лотов меньше 30 они широкие, различия конфигураций надо считать неподтверждёнными.

## Что входит в набор сейчас

7 **синтетических** лотов (`synthetic: true`), составленных для проверки каркаса: недоверенный дешёвый поставщик, рабочие дни вместо календарных, бюджет с доставкой, демпинг без обеспечения и с обеспечением, лот без победителя, цены с НДС и без. Правила демпинга в них взяты из условий самого лота, а не из норматива. Это не датасет для выводов.

## Как собрать настоящий набор (20-30 лотов и больше)

1. Берите лоты с публичного портала: объявление, техническая спецификация, поданные предложения.
2. Записывайте способ закупки и редакцию Правил на дату лота. Пороги демпинга зависят от способа и вида предмета, брать их надо из действующего текста Правил.
3. Эталон размечают двое независимо (`gold`), расхождения разбирают. `--check-gold` ловит только арифметические ошибки, а не ошибки понимания.
4. Протокол итогов комиссии используйте как контрольную точку, а не как истину: комиссии тоже ошибаются.
5. Не допускайте, чтобы лоты писала та же модель, которую потом проверяют.

## Что каркас показывает о конфигурации `bukva`

Проверено на имитации модели с принудительными ошибками (`mock-noisy`):

- Оборванный JSON, выдуманное ограничение (без цитаты в тексте), пропущенный ключ, порог демпинга без базы: `bukva` отказывает. `simple` в этих случаях либо отказывает по невалидному JSON, либо молча применяет выдуманное ограничение.
- **Пропущенное ограничение** (модель написала `null`, а в тексте оно было) и **неверно прочитанная цена** ядро обнаружить не может. Доля уверенно неверных ответов на них у `bukva` и `simple` одинакова.

Вывод: проверка снижает часть ошибок и повышает долю отказов (цена - ложные отказы), но не заменяет качество извлечения. Реальное соотношение на настоящих лотах покажет только прогон.
